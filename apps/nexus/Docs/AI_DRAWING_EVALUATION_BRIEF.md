**Owner:** Hari Babu

## 0. READ THIS FIRST — Cost Guardrails

This feature calls paid third-party APIs. The following are **hard rules**, not
suggestions. Violating any of them can turn a ₹500/month feature into a ₹50,000
bill overnight.

### STOP AND ASK before doing any of these

Claude Code must **pause and ask Hari explicitly** before:

1. Making **any** live API call to a paid model provider — including a single
   "just to test it" call.
2. Running a batch or loop that calls a paid API more than **once**.
3. Processing the existing **81-item Drawing Reviews backlog** through any model.
4. Starting a **fine-tuning job** on Vertex AI or anywhere else. Tuning jobs bill
   on training tokens × epochs and cannot be cancelled cheaply once started.
5. Generating images at resolutions **above 1K**.
6. Adding any new paid dependency, API key, or cloud service.
7. Changing the model ID in config to a higher-tier model.

When asking, state: estimated number of calls, estimated cost, and what happens
if it fails halfway.

### Non-negotiable implementation rules

| Rule | Why |
|---|---|
| **All development and testing uses fixtures.** Store recorded API responses in `__fixtures__/` and replay them. Zero live calls in dev, in tests, or in CI. | A test suite that hits a real API will run hundreds of times |
| **Live calls only behind `AI_EVAL_ENABLED=true`**, defaulting to `false` in every environment including production until Hari flips it. | Kill switch |
| **Cache every generated image by prompt hash.** On cache hit, never regenerate. | Reference images are per-question, not per-student |
| **Never generate an image per submission or per student.** Reference images belong to the question, and are reused by every student who attempts it. | This is the single biggest cost trap in the whole feature |
| **Never use an image-generation model to annotate a student's sheet.** Annotations are coordinates rendered on canvas. See §4. | Image models redraw the sheet instead of marking it; also costs money for a worse result |
| **Hard monthly spend cap set on the API key** at the provider console. Document the value in `.env.example` comments. | Runaway loop protection |
| **Every API call logged** to `ai_call_log` with model, token counts, estimated cost, latency, and the calling context. | You cannot control what you cannot see |
| **Per-day call ceiling in code** (default 300). Exceeding it fails closed and alerts, it does not silently continue. | Second layer of runaway protection |
| **Batch API for any backfill work.** Async, ~50% cheaper, and backfill is never urgent. | Backfilling the question bank |

### Expected scale — sanity check any estimate against this

- ~100–200 students per year
- Assignment roughly every alternate day
- 8–22 submissions per assignment (observed)
- **≈ 2,500–3,000 drawing evaluations per year** ≈ 200–250/month
- ~20–30 distinct recurring brief types across the whole syllabus

If a cost estimate comes out above **US$15/month** at this volume, something is
wrong with the design. Stop and flag it rather than proceeding.

## 1. Problem

Teachers currently grade drawing submissions manually. Two pain points:

1. Grading is slow and the backlog grows (81 pending at time of writing).
2. A previous Gemini integration produced generic art-critique feedback that does
   not match how Hari actually evaluates NATA drawing sheets.
3. Reference images for questions are generated by copy-pasting a prompt into the
   Gemini web UI, downloading, and re-uploading. Pure manual overhead.

## 2. Goal

Model drafts an evaluation → Hari or a teacher reviews and corrects → corrections
are stored as structured data → future evaluations retrieve those corrections as
anchors and get closer to Hari's judgement over time.

**Explicit non-goal:** full automation. A released score must be defensible to a
parent. The target is reducing ~5 minutes per sheet to ~20 seconds of review.

---

## 3. Core architecture — anchors, not fine-tuning

The brief set is small and recurring ("One point perspective subtractive cubes"
appears repeatedly in the assignment list). So the system is built around a
per-brief **anchor set** rather than a general evaluator.

For each brief type, 5 sheets are graded by Hari at score levels 1–5 with full
annotations. Those 5 become the anchors for that brief, permanently.

At evaluation time the request contains:
- the student's sheet
- the 5 anchor sheets with Hari's annotations and comments
- the criterion definition being scored
- (optionally) recent corrections on this brief

The model is asked **where the new sheet falls relative to the anchors**, not for
an absolute score. LLMs are substantially better at relative comparison than
absolute scoring on subjective work.

Anchors are identical across every submission for a given brief → they are the
ideal thing to put in a **prompt cache**. Implement caching from day one; it is
the main cost lever at our volume.

**Fine-tuning is out of scope for v1.** Revisit after ~12 months of accumulated
corrections. Do not build for it now beyond keeping the export clean (§7).

## 4. Annotation contract

Model returns **coordinates**, app renders them. Never generated images.

```ts
type Marker = 'problem' | 'good' | 'guide' | 'note';

interface Annotation {
  type: 'region' | 'point' | 'line' | 'stroke';
  // ALWAYS normalized 0–1, origin top-left.
  // Region uses [x, y, w, h]. Line/stroke use [[x,y], ...].
  geometry: number[] | number[][];
  marker: Marker;
  criterionKey: string;
  comment: string;
}

interface CriterionResult {
  criterionKey: string;
  band: 1 | 2 | 3 | 4 | 5;
  reasoning: string;        // must cite what is visible in the sheet
  closestAnchorBand: number;
  confidence: 'high' | 'medium' | 'low';
  annotations: Annotation[];
}

interface EvaluationResult {
  criteria: CriterionResult[];
  totalScore: number;       // out of 5, per existing UI
  overallComment: string;
  flags: ImageQualityFlag[];
}
```

**Coordinate normalization happens in the provider adapter, never downstream.**
Different providers use different conventions (`[x0,y0,x1,y1]` vs `[x,y,w,h]`,
normalized vs pixel-absolute). If raw provider coordinates ever reach the
database, the entire correction history becomes provider-locked and worthless on
a model switch.

Annotations are stored as **vectors, never flattened pixels**. Flatten only for
display and for future training export.

## 5. Data model (Supabase)

```sql
-- Reusable brief types: "one-point perspective subtractive cubes" etc.
brief_type
  id, key, title, description, criteria_keys jsonb, created_at

-- What is being graded, per brief
criterion
  key, brief_type_id, title,
  observable_checks jsonb,   -- concrete, verifiable statements
  band_descriptions jsonb    -- bands 1–5 in Hari's own words

-- The 5 graded reference sheets per brief
anchor_sheet
  id, brief_type_id, band, submission_id,
  image_path, annotations jsonb, comment, created_by, is_active

evaluation
  id, submission_id, brief_type_id,
  status,                    -- draft | reviewed | released
  provider, model_id, prompt_version,
  raw_response jsonb,        -- keep for debugging model drift
  ai_total, final_total,
  created_at, reviewed_by, reviewed_at

evaluation_criterion
  evaluation_id, criterion_key,
  ai_band, final_band, was_corrected boolean

annotation
  id, evaluation_id, criterion_key,
  source text,               -- 'ai' | 'human'
  action text,               -- 'created' | 'moved' | 'deleted' | 'kept'
  geometry jsonb, marker, comment

ai_call_log
  id, evaluation_id, provider, model_id, operation,
  input_tokens, output_tokens, cached_tokens,
  estimated_cost_usd, latency_ms, success, error, created_at
```

`source` + `action` on `annotation` is the training signal. It records not just
that Hari disagreed but *where* and *how*.

## 6. Provider adapter

Model choice must never leak past this boundary.

```ts
interface EvaluationProvider {
  id: string;
  evaluate(input: EvaluationInput): Promise<EvaluationResult>;
  generateReferenceImage(prompt: string, opts: ImageOpts): Promise<ImageResult>;
  capabilities: {
    spatialGrounding: boolean;   // can it locate things accurately?
    schemaConstrained: boolean;  // real JSON schema enforcement?
    maxImages: number;
    supportsPromptCache: boolean;
  };
}
```

Adapter responsibilities: build the request, parse, repair malformed JSON, validate
against schema, normalize coordinates, log cost. On validation failure: retry once,
then mark the evaluation `needs_manual` — never write a half-parsed record.

Start with Gemini. The adapter exists so switching later is a config change, not a
rewrite. **Do not build additional providers speculatively** — build the interface,
implement one.

## 7. Rollout — three stages, gated by Hari

**Stage 1 — Shadow.** Model evaluates, only Hari sees output, teachers grade
normally. Purpose: measure agreement. Nothing reaches students.

**Stage 2 — Assist.** Draft is pre-filled in the review UI. Reviewer approves or
corrects, then releases. This is where the time saving and the training data both
come from. *This is the target end state for v1.*

**Stage 3 — Auto with escalation.** Deferred. Do not build.

**Holdout set:** 50 sheets Hari grades that are never used as anchors and never
fed back. Re-run after every prompt or model change to detect regressions.
Subjective-task regressions are silent otherwise.

**Feedback weighting:** corrections are the signal; bare approvals are mostly
noise. Weight corrections heavily and sample approvals lightly when building any
future training export.

## 8. Reference image generation

Separate concern from evaluation. Removes the copy-paste loop.

Flow: teacher enters question → backend generates an image prompt from it using a
cheap text model with house style appended → image API call → stored in Supabase
storage → thumbnail shown for approval → teacher approves or regenerates.

- Store the generating prompt alongside the image (reproducibility, bulk restyle)
- Hash the prompt; cache hit = no regeneration, ever
- 1K resolution only
- Background job, not request thread
- `status: pending_review` — nothing reaches students unapproved. Image models
  produce impossible perspective, which is fatal when the subject *is* perspective
- Batch API for backfilling the existing question bank

## 9. Build order

1. Schema + migrations. No API calls.
2. Annotation rendering + editing on canvas, working with hand-entered fixture
   data. Prove the sketch tool and AI annotations share one layer.
3. Anchor management UI — mark a graded submission as an anchor for a brief.
4. Provider adapter with fixtures only. Full test coverage, zero live calls.
5. **CHECKPOINT — ask Hari before first live call.**
6. Single live call on one sheet. Inspect. Compare cost estimate to actual.
7. Shadow mode on one brief type.
8. Review UI, then Stage 2.
