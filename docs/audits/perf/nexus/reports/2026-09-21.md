## Performance audit report

1. **Top problems:**
   - PERF-0001: hydration fails on every warm-cache load;
   - PERF-0003: no deadline on the Graph identity check;
   - PERF-0004: no deadline on database hops;
   - PERF-0007: Cloudflare proxies Nexus;
   - PERF-0008: Node 24 under Next 14.2;
   - PERF-0005: failed lookups reported as "User not found" or 401;
   - PERF-0002: the papers page shows a false "not found" with no retry;
   - PERF-0009: auth caches expire before the next poll;
   - PERF-0006: poller stacking and stale counts;
   - PERF-0010: about 14 queries per badge poll.
2. **Root cause of React #418 and #423** (measured):
   - The instant-boot change (`9d441825`) seeds user, role, classrooms and `dbLoading` from a localStorage copy of `/api/auth/me` inside `useState` initialisers.
   - The server has no localStorage, so it renders RoleGuard's "Loading..." spinner. A browser with a warm cache renders the signed-in page on its first render.
   - The trees differ, so hydration fails (#418). No Suspense boundary sits above the shell, so React discards the server HTML and renders the whole root again on the client (#423).
   - The test reproduces the exact messages.
3. **Root cause of the 524s:**
   - Measured: Cloudflare is in the request path (`Server: cloudflare`, `x-vercel-id: bom1::sin1`). The database is fast: the unread count averages 0.0ms, the users lookup 0.06ms, and the slowest statement ever recorded took 227ms.
   - Measured: no outbound call in the chain had a timeout.
   - Inferred: a stalled Graph or proxy hop held requests past Cloudflare's 100s. Which hop stalled could not be confirmed without Vercel logs.
   - The 404s were not missing users: a failed users lookup was reported as "User not found".
4. **Why refresh fixes it:**
   - The page stays on skeletons for exactly as long as a request stays open, and a stalled request stays open up to 100s.
   - A refresh starts fresh requests that usually land on healthy calls.
   - The hydration failure also remounted the whole app on every hard load, so every provider and poller started from scratch.
5. **Slowest APIs:** `/api/notifications` and `/api/nav-badges` p50/p95 not measured, because Vercel logs were unavailable. The slow step is an outbound hop, not SQL.
6. **Duplicate requests:**
   - `/api/auth/me` has one owner (`useNexusAuth`). Clean.
   - The nav-badges poller stacked requests on a hung one and could apply an older response over a newer one. Fixed (PERF-0006).
   - The shared notifications poller already had an in-flight guard.
7. **Largest components and bundles:** not in scope this session. `useNexusAuth.tsx` is about 950 lines, and the papers page reaches 57 own files.
8. **Database and query bottlenecks:**
   - None in SQL. All filters are indexed and the tables are small.
   - Cost comes from round trips through the proxy: about 14 per staff badge poll, and a users lookup on almost every poll.
   - `idx_users_ms_oid` duplicates `users_ms_oid_key`.
9. **Most expensive renders:** the whole-root client re-render on every hard load (#423). Removed by PERF-0001.
10. **Recommended fixes:** see Findings, under fix.
11. **Estimated impact:**
    - PERF-0001 removes both console errors and one full render of the tree per hard load.
    - PERF-0003 and PERF-0004 bound a stalled hop at 8 to 10s instead of 100s.
    - PERF-0007 removes the 524 path entirely.
12. **Risk of each change:** per finding, under risk.
13. **Implementation order:**
